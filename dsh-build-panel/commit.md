## 第1步：代码检查

先执行 `git diff --cached` 和 `git diff`，分别获取暂存区与工作区的变更内容（输出为空即表示该区域无变更），再检查是否存在问题：

**检查要点**：
- 是否存在明显的 bug 或逻辑错误
- 是否存在未使用的导入、变量或死代码
- 是否存在硬编码的敏感信息（密钥、token、密码等）
- 是否存在可能的空值引用或类型安全问题
- 是否存在遗留的调试代码（console.log、debugger 等）
- 代码风格是否与项目一致

**检查结果处理**：
- 如果没有问题，直接进入第2步提交，不需要用户确认
- 如果存在问题，列出所有问题并**询问用户是否仍要继续提交**，等待用户确认后再执行

## 第2步：生成提交信息并提交

根据以上 diff 生成提交信息，并提交代码。

## 提交格式（按优先级排序）

1. **标准格式**: `cx/trip#任务号 简要描述`
   示例: `cx/trip#9348 火车票发票的问题处理`

2. **带模块路径格式**: `cx/trip#任务号 中台--一级模块--二级模块--具体描述【相关人员】`
   示例: `cx/trip#9376 中台--财务--收款认领--人工录入、转领生成的收款单--展示转领、退款操作【凌总】`

3. **conventional commits 格式**（无任务号时）: `type: 简要描述`
   示例: `feat: 酒店订单详情显示roomProdName` / `fix: 修复baggageInfo为null导致编辑行程报错`
   type 可选:
   - `feat`: 新增 feature
   - `fix`: 修复 bug
   - `docs`: 仅仅修改了文档，比如 README, CHANGELOG, CONTRIBUTING
   - `style`: 修改了空格、格式缩进、逗号等，不改变代码逻辑
   - `refactor`: 代码重构，没有加新功能或者修复 Bug
   - `perf`: 优化相关，比如提升性能、体验
   - `test`: 测试用例，包括单元测试、集成测试等
   - `chore`: 改变构建流程、或者增加依赖库、工具等
   - `revert`: 回滚到上一个版本

## 要求
- 任务号缺失时，优先使用格式3
- 描述用中文，简洁明确
- 涉及具体功能模块时，用 `--` 分隔层级
- 有任务号用格式1或2，无任务号用格式3

## 提交信息结构规范

- **第一行**：按上述格式之一编写，作为标题行
- **body（可选）**：当需要补充详细变更点时，在标题行后空一行，用 `-` 列表逐条罗列
- 示例：
  ```
  docs: 更新 build 命令文档，完善参考文件索引、待办事项及完成流程规范

  - 主/备选双层参考文件索引策略
  - 待办文件命名与元数据格式要求
  - 已完成事项转移校验与防覆盖规则
  ```
